Autonomous mode is enabled for new installations and lets LUMI run agent-selected operations without per-tool approval prompts. Execution policy, hooks, workspace and lane authority, and lifecycle checks still run. With autonomous mode off, Auto Approve settings decide which eligible operations can run automatically.

Use Auto Approve settings to tune routine permissions when you want more control than autonomous mode provides.

## How It Works

Every invocation is evaluated by `ExecutionFunnel`. In autonomous mode, consent declarations and risk markers are recorded for audit, and the agent proceeds without a per-tool approval prompt. Execution policy, hooks, workspace and lane authority, cancellation, and lifecycle checks still decide whether dispatch is allowed. Outside autonomous mode, the per-capability settings, command policy, trusted-command rules, MCP policy, and handler eligibility decide whether an operation can run automatically.

A few details matter:

- **Workspace vs outside workspace**: "Read all files" and "Edit all files" only extend the base toggle. If the base toggle is off, the "all files" option does nothing.
- **Terminal commands**: `requires_approval` is an optional risk marker and defaults to `false`. In autonomous mode, `true` is recorded for audit and never pauses execution. Run the action when the user's task clearly authorizes its target and scope; skip unrelated or unclear external/system actions and continue with in-scope work. With autonomous mode off, `true` requests explicit consent. The flag does not bypass command-permission policy or execution hooks.
- **Notifications**: If enabled, LUMI sends OS-level notifications when approval is required, and when an auto-approved terminal command has been running for 30 seconds.

## Permissions

| Setting | What It Allows |
|---------|----------------|
| Read project files | Read files, list files, search in your workspace |
| Read all files | Read files outside your workspace (requires base toggle) |
| Edit project files | Create and edit files in your workspace |
| Edit all files | Edit files outside your workspace (requires base toggle) |
| Execute safe commands | Run terminal commands marked safe |
| Execute all commands | Auto-approve eligible commands outside autonomous mode |
| Use the browser | Browser tool for web fetching and searching |
| Use MCP servers | MCP tools and resources |
| Enable notifications | Notifies you about long-running commands |

<Warning>
"Read all files" and "Edit all files" only matter if their base toggle is enabled. They extend access outside your workspace.
</Warning>

## Command Risk and Policy

With autonomous mode off, LUMI classifies the exact normalized command centrally. Read-only and verification tiers can use **Execute safe commands**; trusted commands and **Execute all commands** follow their respective policies. In autonomous mode, command classification remains available for audit and policy, while `requires_approval=true` does not create a consent pause.

**Commonly treated as safe:**
- `npm run build`, `npm test` - Build/test output
- `git status`, `ls -la`, `cat package.json` - Read-only commands

**Skip when outside the user's requested scope:**
- `rm -rf <path>` - Deletes user data or files outside the task's target
- `mv <a> <b>` - Overwrites or moves files outside the requested workspace changes
- Commands that change system settings or credentials, publish/deploy, or send data to external services

An install or in-place edit that is explicitly part of the requested workspace task can proceed as routine work; the agent should not turn every file modification into a consent prompt.

## Autonomous mode

Autonomous mode lets LUMI proceed with agent-selected work without asking the user to approve each tool call. Approval declarations remain auditable. Execution hooks, operation policy, workspace fencing, lane authority, and the execution permit remain active.

<Note>
Autonomous mode also reduces clarification prompts. Turn it off to make per-capability Auto Approve settings and handler eligibility authoritative for automatic execution.
</Note>

### What Gets Auto-Approved

When autonomous mode is enabled, the agent may proceed with best judgment rather than asking task-clarification questions. Handler eligibility and risk stay visible in the audit record; the agent's operations do not pause for consent.

### When to Use Autonomous Mode

**Rapid prototyping** where you want low friction and can review the resulting changes.

**Trusted, repetitive tasks** where you've validated LUMI's approach and want to eliminate approval overhead.

**Demonstration purposes** where you want to show LUMI's capabilities without interruptions.

Use checkpoints or version control when you want a quick way to inspect or restore autonomous workspace edits. Autonomous mode does not pause for `requires_approval=true`; skip actions outside the user's clear request or with an uncertain target/scope.

## Implementation (code paths)

| Setting | Storage key | Effect |
|---------|-------------|--------|
| Per-category auto-approve | `autoApprovalSettings` | Allows `ExecutionFunnel` to record automatic approval when the complete intent and policy are eligible |
| Autonomous mode | `yoloModeToggled` (global state) | Changes prompt/follow-up behavior and admits agent-selected operations without per-tool consent prompts |

**Code:**

- Settings persistence: `src/core/controller/state/updateSettings.ts`
- YOLO prompt behavior: `src/core/prompts/system-prompt/` variants (e.g. `next-gen/template.ts`)
- Sole approval/permit gate: `src/core/task/tools/execution/ExecutionFunnel.ts`
- Pure handler contract: `src/core/task/tools/types/ToolContracts.ts`
- MCP per-tool setting: evaluated by `ExecutionFunnel` from `mcpHub.connections`

Autonomous mode removes per-operation consent prompts. Hooks, command and operation policy, workspace fencing, lane authority, task lifecycle, and invocation-scoped permits still govern dispatch. Use [checkpoints](/core-workflows/checkpoints) to inspect and restore workspace changes.
