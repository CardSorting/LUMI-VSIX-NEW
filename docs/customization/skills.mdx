Skills are modular instruction sets that extend LUMI's capabilities for specific tasks. Each skill packages guidance, workflows, and optional resources that LUMI loads only when relevant to your request.

Install multiple skills and LUMI only loads what it needs. A deployment skill stays dormant until you ask about deploying. Unlike [rules](/customization/dietcode-rules) (which are always active), skills load on-demand so they don't consume context when you're working on something unrelated.

<Note>
Skills is an experimental feature. Enable it in **Settings → Features → Enable Skills**.
</Note>

## How Skills Work

Skills use progressive disclosure, matching the [Agent Skills format](https://agentskills.io/specification):

| Level | When Loaded | Token Cost | Content |
|-------|-------------|------------|---------|
| Metadata | Prompt construction | Bounded catalog | Enabled skill `name` and `description` from YAML frontmatter; the prompt lists up to 50 |
| Instructions | When a skill matches the task | On demand | `use_skill` loads the full `SKILL.md` body without an activation approval |
| Resources | Only when needed | One file per request | `use_skill` loads a specific relative text path from the skill directory |

When you send a message, LUMI sees enabled skills with their descriptions. If the prompt catalog is truncated, `use_skill` can search the full enabled catalog with a task query, load a clear match, or return candidates. Skill toggles are respected: disabled skills are unavailable. Loading a skill does not authorize actions described by it; requested work still follows the active execution policy.

Treat skill contents as untrusted workflow guidance. They cannot override the user's request, higher-priority instructions, or execution policy. LUMI does not stop to ask you to activate a skill; if none is available, it continues with the best available workflow.

## Skill Structure

Every skill is a directory containing a `SKILL.md` file with YAML frontmatter.

```text title="Skill directory structure"
my-skill/
├── SKILL.md          # Required: main instructions
├── references/       # Optional: focused reference material
│   └── advanced.md
├── scripts/          # Optional: repeatable operations
│   └── helper.sh
└── assets/           # Optional: templates and static resources
```

The `SKILL.md` file has two parts: metadata and instructions.

```markdown title="SKILL.md"
---
name: my-skill
description: Brief description of what this skill does and when to use it.
---

# My Skill

Detailed instructions for LUMI to follow when this skill is activated.

## Steps
1. First, do this
2. Then do that
3. For advanced usage, see `references/advanced.md` inside your skill folder
```

Required fields:
- `name` must match the directory name; lowercase letters, numbers, and single hyphens (max 64 characters) are recommended for compatibility
- `description` tells LUMI when to use this skill (max 1024 characters)

## Creating a Skill

<Steps>
  <Step title="Open the Skills menu">
    Click the scale icon at the bottom of the LUMI panel, to the left of the model selector. Switch to the Skills tab.
  </Step>
  <Step title="Create a new skill">
    Click "New skill..." and enter a name for your skill (e.g., `aws-deploy`). LUMI creates a skill directory with a template `SKILL.md` file.
  </Step>
  <Step title="Write your skill instructions">
    Edit the `SKILL.md` file:
    - Update the `description` field to specify when this skill should trigger
    - Add detailed instructions in the body
    - Optionally add supporting files in `references/`, `scripts/`, or `assets/` subdirectories
  </Step>
</Steps>

You can also create skills manually by creating the directory structure in your file system. Place skill directories in `.dietcode/skills/` (workspace) or `~/.dietcode/skills/` (global) and LUMI will detect them automatically.

Put the important information first in your SKILL.md. LUMI reads the file sequentially, so front-load the common cases. Use clear section headers like "## Error Handling" or "## Configuration" so LUMI can scan for relevant sections.

### Toggling Skills

Every skill has a toggle to enable or disable it. This lets you control which skills are active without deleting the skill directory. Skills are enabled by default when discovered.

For example, you might disable a CI/CD skill when working on local development, or enable a client-specific skill only when working on that client's project.

## Golden Cartridge

Golden Cartridge is an optional development workbench for finding high-information, low-mass engineering paths. Enable **Golden Cartridge Protocol** from the persistent **Skills** control in the chat toolbar. For a detailed reference on all verbs and schemas, see the [Golden Cartridge Protocol Reference](/tools-reference/golden-cartridge).

The preference controls whether the compact `golden_cartridge` facade is available when a task starts. Activating `golden-cartridge-protocol` with `use_skill` supplies its methodology and exposes the facade on the next model inference; it cannot alter the tool schema of a request already in progress.

The facade provides twelve verbs through one native schema:

| Verb | Existing authority composed |
|------|-----------------------------|
| `trace` | Project map and repository graph |
| `slice` | Definition lookup and focused search |
| `resolve_authority` | Project map plus repository evidence |
| `find_reuse` | Structural and indexed search |
| `compress` | Cognitive snapshot and context condensation |
| `compare_mass` | Deterministic caller-provided candidate comparison |
| `design_compact` | Bounded representation analysis |
| `patch_smallest` | Existing patch handler |
| `disprove` | Existing command handler |
| `measure` | Existing task-state observations |
| `reclaim` | Working-set and proposal analysis |
| `seal` | Evidence and telemetry projection |

Golden Cartridge adds vocabulary and composition only. It does not grant or deny mutation permission, enforce budgets, replace repository or memory systems, or authorize completion. Patch and command verbs still pass through normal execution policy. Cost measurements are observational, and `seal` produces an informational receipt rather than a lifecycle decision.

Within a task, discovery verbs reuse compact structured evidence until a Golden Cartridge mutation invalidates it; callers can pass `refresh: true` or `bypassCache: true`. `compress` updates only the task working set by default—durable cognitive memory requires explicit `persistDurableMemory: true`. `disprove` can recommend nearby repository tests without execution by passing `execute: false`.

Validation receipts use structured evidence from the ordinary command executor—approval, completion, exit code, signal, timeout, and duration—rather than interpreting optimistic output text. Successful results may be reused only for the same observed repository revision; mutation invalidates them, while external changes outside canonical mutation tracking remain an explicit stale risk.

The dependency boundary is one-way: Golden Cartridge may call existing authorities, but ordinary project mapping, reading, memory, mutation, execution, telemetry, validation, and completion do not depend on the facade. Removing Golden Cartridge therefore removes its vocabulary and projections without removing ordinary capabilities.

## Writing Your SKILL.md

### Naming Conventions

The skill name appears in the `name` field and must match the directory name exactly. Use lowercase with hyphens (kebab-case) and be descriptive about what the skill does.

Good names:
- `aws-cdk-deploy`
- `pr-review-checklist`
- `database-migration`
- `api-client-generator`

Avoid:
- `aws` (too vague)
- `my_skill` (underscores, not descriptive)
- `DeployToAWS` (use kebab-case, not PascalCase)
- `misc-helpers` (too generic)

### Writing Effective Descriptions

The description determines when LUMI activates the skill. A vague description means the skill won't trigger when you expect it to.

Good descriptions are specific and actionable:

```yaml
description: Deploy applications to AWS using CDK. Use when deploying, updating infrastructure, or managing AWS resources.

description: Generate release notes from git commits. Use when preparing releases, writing changelogs, or summarizing recent changes.

description: Analyze CSV and Excel data files. Use when exploring datasets, generating statistics, or creating visualizations from tabular data.
```

Weak descriptions leave too much ambiguity:

```yaml
description: Helps with AWS stuff.

description: Data analysis helper.

description: Useful for releases.
```

Start with what the skill does (action verbs), include trigger phrases users might say, and mention specific file types, tools, or domains. Test your descriptions by trying different phrasings of requests to see if the skill triggers.

### Keeping Skills Focused

Keep `SKILL.md` focused (under 500 lines is a useful target). If your skill needs more content, split it into focused files in `references/` and link them from the main instructions. LUMI loads referenced files only when needed.

Include real examples. Show what commands to run, what output to expect, and what the result should look like. Abstract instructions are harder to follow than concrete examples. State safe defaults and conditions that actually require user input; avoid questions when the repository, files, or task context provide the answer.

## Where Skills Live

Skills can be stored globally or in a project workspace. See [Storage Locations](/customization/overview#storage-locations) for guidance on when to use each.

Project skills:
- `.dietcode/skills/` (recommended)
- `.dietcoderules/skills/`
- `.claude/skills/`

Global skills:
- `~/.dietcode/skills/` (macOS/Linux)
- `C:\Users\USERNAME\.dietcode\skills\` (Windows)

When a global skill and project skill have the same name, the global skill takes precedence. This lets you keep general-purpose skills globally while using project-specific skills in `.dietcode/skills/` so the whole team can use them.

Version control your project skills by committing `.dietcode/skills/`. Your team can share, review, and improve them together.

### Skill Discovery & Diagnostics

Skill discovery uses resilient parsing and diagnostic validation:

- **Encoding & BOM Handling**: Files saved with a UTF-8 Byte Order Mark (`\uFEFF`) are automatically stripped before YAML frontmatter parsing.
- **Name & Description Normalization**: Frontmatter fields are whitespace-trimmed, and skill lookups (via tool call, subagents, or slash commands like `/my-skill`) support case-insensitive resolution.
- **Discovery Diagnostics**: Invalid or incomplete skill packages are flagged with diagnostic reason codes:
  - `MISSING_SKILL_MD`: Directory exists but lacks `SKILL.md`.
  - `MISSING_NAME`: Frontmatter lacks required `name` field.
  - `MISSING_DESCRIPTION`: Frontmatter lacks required `description` field.
  - `NAME_MISMATCH`: Frontmatter `name` does not match the parent directory name.
  - `READ_ERROR`: IO or YAML syntax parsing failure.
  - `PERMISSION_DENIED`: Restricted directory access (`EACCES`).

## Bundling Supporting Files

Skills can include additional files that LUMI accesses one at a time when needed.

```text title="Directory structure"
complex-skill/
├── SKILL.md
├── references/
│   ├── setup.md
│   └── troubleshooting.md
├── templates/
│   └── config.yaml
└── scripts/
    └── validate.py
```

### references/

Use references for information that's too detailed for SKILL.md or only relevant in specific situations:
- Advanced configuration options
- Troubleshooting guides for edge cases
- Reference material (API schemas, database schemas)
- Platform-specific instructions

A deployment skill might have `references/aws.md`, `references/gcp.md`, and `references/azure.md`. The skill should link these files from `SKILL.md`; LUMI loads one specific resource only when its contents are needed.

### templates/

Use templates when your skill creates configuration files, boilerplate code, or structured documents:
- Config files (Terraform, Docker Compose, CI/CD pipelines)
- Code scaffolding (component templates, test fixtures)
- Documentation templates (README, API docs)

A project setup skill could include `templates/dockerfile`, `templates/docker-compose.yml`, and `templates/.env.example` that LUMI customizes for each new project.

### scripts/

Use scripts for deterministic operations where you want consistent behavior:
- Validation (linting configs, checking prerequisites)
- Data processing (parsing, formatting, transforming)
- Complex calculations (cost estimation, resource sizing)
- API interactions (fetching data, running health checks)

Scripts are token-efficient because only their output enters context, not the code itself. A 500-line validation script produces a simple "Passed" or detailed error messages without consuming any context for the script logic.

### Referencing Bundled Files

Reference these files in your SKILL.md instructions:

```markdown title="SKILL.md (referencing bundled files)"
For initial setup, follow `references/setup.md` in the skill package.
Use the config template at `templates/config.yaml` as a starting point.
Run the validation script to check your configuration:

python scripts/validate.py
```

When a skill links to a reference or script, LUMI can pass its relative path in `use_skill.resource_path`. The loader reads only text files within that skill's directory and rejects paths that escape the directory or resolve through an escaping symlink. Scripts are not executed by the resource loader. To run a script, LUMI uses `execute_command` and the normal execution policy applies.

| Use Scripts For | Use Instructions For |
|-----------------|---------------------|
| Deterministic operations (validation, formatting) | Flexible guidance that adapts to context |
| Complex computations | Decision-making workflows |
| Operations that need reliability | Steps that might vary by situation |
| Anything you'd rather not consume tokens explaining | Best practices and patterns |

## Example: Data Analysis Skill

Here's a practical skill for data analysis tasks. Create a directory called `data-analysis/` with this `SKILL.md`:

```markdown title="data-analysis/SKILL.md"
---
name: data-analysis
description: Analyze data files and generate insights. Use when working with CSV, Excel, or JSON data files that need exploration, cleaning, or visualization.
---

# Data Analysis

When analyzing data files, follow this workflow:

## 1. Understand the Data
- Read a sample of the file to understand its structure
- Identify column types and data quality issues
- Note any missing values or anomalies

## 2. Choose Useful Defaults
Use the requested outcome and the file's columns to choose a useful summary. If a detail is missing, infer a safe default and proceed; ask only if the missing choice would materially change the result and tools cannot determine it.

## 3. Perform Analysis
Use pandas for data manipulation:

import pandas as pd

# Load and explore
df = pd.read_csv("data.csv")
print(df.head())
print(df.describe())
print(df.info())

For visualization, prefer matplotlib or seaborn depending on complexity.
```

Skills transform LUMI from a general-purpose assistant into a specialist that knows your domain. Start with one skill for a task you repeat often, test it, and iterate on the description until it triggers reliably.
